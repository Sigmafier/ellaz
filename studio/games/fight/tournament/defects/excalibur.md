# excalibur cell - defects log

One line per defect hit while building the Excalibur 0.32 arm: what it was, and
the class it belongs to. Honest and specific, because this log is a ranking
input - a short log is only worth something if it is short because the engine
behaved.

## Defects

- 2026-09-12 `TextureLoader._MAX_TEXTURE_SIZE` is a STATIC that ships at **4096** and is only replaced with the device's real `gl.getParameter(MAX_TEXTURE_SIZE)` when a GL context is registered. `ImageSource.load()` checks an image against that static, so loading a sheet before the Engine exists reports our 4900x3300 atlas as too large for the device - as a `console.error`, which the admission gate counts as a DISQUALIFICATION, on hardware where the real limit is comfortably above it (the same run later logs the softer "may not work on all mobile devices" warn once the context IS registered, which is the honest reading). Class: a guard reading an uninitialised static, and a library's soft failure being the harness's hard failure. Fixed by constructing and starting the Engine FIRST inside `load()`, then loading the sheets.
- 2026-09-12 `ExcaliburGraphicsContext.flush` does not paint in call order. With `useDrawSorting` on (the WebGL default) it sorts by z and then GROUPS BY RENDERER - `originalSort` is each renderer's first appearance - so at one z the arena rectangles and the HUD rectangles batch together and the sprites land on the wrong side of both. With `useDrawSorting` off it is worse: `flush` walks `this._renderers.values()` and drains each renderer whole, so interleaving is lost entirely. Class: a batcher re-deciding an order the caller expressed by call sequence (the same shape the phaser lane logged for a display list, from the other direction - there insertion order was remembered, here it is discarded). Fixed with one z band per harness call (arena 0, shadows 1, sprites 10+i, fx 100+i, hud 2000, text 2001, boxes 3000); within a band the sort is stable, so the plan's own order survives.
- 2026-09-12 the harness draws `drawBoxes` AFTER `drawHud`, and the HUD must not shake while the boxes must. In this arm that is neither a save/restore (canvas) nor a parenting decision (pixi) but a THIRD thing: the shake is a `ctx.translate` around two separate groups, with the HUD painted between them under an untranslated save. Class: draw order and transform are one decision in immediate mode and two in retained mode - and three in an immediate-mode painter driving a sorted queue.
- 2026-09-12 `engine.start()` is async and `mount()` is not, so the obvious shape floats a promise into `mount` where a rejection becomes an unhandled rejection nobody attributes. Class: a lifecycle the contract does not have a slot for. Handled by doing the whole engine boot inside `load()`, which the harness awaits.
- 2026-09-12 MY OWN instrument, and the worst of the day: "open both arms, wait, shoot" is not the same moment, so the pixel diff had to replace `requestAnimationFrame` AND `performance.now` with a pumped clock at exactly 1000/60 ms a frame. That is not sufficient on its own here - **excalibur registers its rAF callback during `load()`, BEFORE the harness registers its own**, so inside one pumped frame the engine runs first and paints the PREVIOUS plan, one tick behind. Read straight, that is a whole-sprite displacement reported as an arm defect. Class: `a-diagnostic-that-truncates-what-it-compares` - a differential whose arms were never held equal. Fixed with two trailing pumps of dt=0, which re-run both callbacks without stepping the sim; the instrument prints the tick beside every shot so a mismatch cannot hide.
- 2026-09-12 and a claim defect inside that fix: I wrote a code comment asserting that `pixelArt: true` cost this arm "54 px of ink along the robot's feet at tick 120, 0 with it off", from ONE build, before running the other arm. The one-variable control refutes it - sampler on and sampler off give **214 / 262 / 241 / 96** differing pixels at ticks 30 / 120 / 300 / 599, identical in count, `worst` and bounding box, because `antialiasing: false` already pins filtering to NEAREST. The comment was wrong for an hour and would have been quoted as a measurement (`a-comment-that-explains-a-cost-must-name-its-measurement`). Class: a cost claim written from reasoning rather than from two arms. The shipped comment now carries both arms and the four ticks.
- 2026-09-12 `page.waitForFunction` polls on `requestAnimationFrame` by default, and the init script had just replaced it - so the wait times out on a page running perfectly. `polling: 100`. Class: a probe that depends on the thing it is replacing. (Inherited from `pixi8.md`; met it anyway, which is what a defect log is for.)
- 2026-09-12 my KO probe served a 6 hp teddy and screenshotted at tick 600, and got a healthy teddy with a FULL bar on both arms - which reads as "the KO never happened". It had: the match's `koFadeTicks` is 60 and `rematchAfterTicks` is 90, so the panel is up for 90 ticks somewhere in the middle and both bars are restored afterwards. Class: sampling a transient state at a fixed time and reading its absence as a fact. Fixed by also serving `koFadeTicks: 1, rematchAfterTicks: 100000` so the panel is held.

## Notes a judge should see (decisions, not defects)

- **Nothing in the engine's update touches the picture.** No Actors, no entities, no physics (`physics: false`), no input, no audio. The harness's draw calls RECORD a plan; `endFrame` publishes it; one `ex.Scene` subclass's `onPostDraw` paints it. Drawing outside the engine's draw lifecycle is explicitly unsupported (it warns), so the cell is immediate-mode inside the one window the engine opens for it.
- **`pixelArt: true` is set and measured to change nothing here** - see the defect above. It is kept because it is the correct declaration for this art, not because it moved a number.
- **`garbageCollection: false`** costs one loud `WebGL Garbage Collection Disabled!!!` warn at boot. Taken deliberately: a background collector is work the plain-canvas bar is not doing, and every texture this arm holds is drawn every frame.
- **Flip is a negative destination offset, not `Graphic.flipHorizontal` alone.** `_flip` mirrors about the graphic's own BOX; the contract says mirror about the PIVOT column. `dx = op.x - (spriteWidth - pivotPx)` when flipped puts the pivot back where the plan asked. Both sheets happen to have a centred pivot, so a box-centre flip would look correct today and be wrong for the first character whose pivot is off-centre. Verified with `?boxes=1`.
- **The pivot comes from `<set>.manifest.json`, not the atlas frame's 0-1 copy.** The bar's `adapters/canvas/draw-frame` reads the manifest; the atlas carries the same fact per frame. Two sources of truth for the feet is how a drift goes silent, so this arm reads the same one the bar does.
- **Boxes are four 1px FILLS, not a stroked rectangle.** The rectangle shader decides fill-vs-stroke by comparing a fragment's position against `v_strokeThickness`, which is its own rounding; four fills cover exactly the pixels the bar's `strokeRect(x+0.5, ...)` covers, by construction. Confirmed: zero differing pixels anywhere on the `?boxes=1` overlay.
- **The HUD's text is the demo brawler's 5x7 bitmap font**, baked once per (string, size, colour) into a canvas the engine uploads as a texture - NOT `ex.Text`/`ex.Font`. A real typeface would be the only thing on screen not snapped to the arena's pixel grid, and the tournament compares arms on the same HUD. The glyph table is duplicated into `cell.ts` rather than imported from `../canvas/font`, for the reason the pixi lane logged: a shared module moves the BAR's `authored` column, which is a number the tournament reads.
- **Console output is four warnings and zero errors**: the GC one above, `Scene update/draw called before initialize for scene root!` (the engine's own root scene while the director is still routing to ours), the softer over-4096 image note, and a GL driver "GPU stall due to ReadPixels" performance message.
- 2026-09-12 inherited from `phaser4.md` / `pixi8.md`: `--outDir` resolves against the vite config's ROOT (`games/fight`), not the cwd, so `../../dist-fight-excalibur` is the correct flag from `cells/`. Cost this lane nothing because it was in the brief; noted so the count of lanes that paid for it stays honest at two.

## What the arm measured

- `run-tape --dist dist-fight-excalibur excalibur` - **ADMITTED**, ticks 600, hash `dfd5d033`, chain `2617d8f2`, eventHash `687c23d3`, zero page errors and zero console errors.
- `assert-equal-work canvas excalibur` - backbuffer 640x360 both, dpr 1 both, drawn 20 both; excalibur reports `drawingBuffer 640x360`, `samples 0`, `antialias false`, version `0.32.0`.
- `bytes` - engine 124,498 gz - shared 10,342 gz - authored 3,538 gz - total 138,378 gz (4 chunks).
- Tick-matched pixel comparison against the bar (`?tape=versus-600&boxes=1`, rAF and `performance.now` replaced by a pumped clock at 1000/60 ms, alpha 0, both arms confirmed at the same tick AND the same state hash), of 230,400 px:

  | tick | differing | worst channel delta | what differs |
  |---|---|---|---|
  | 30 | 214 | **1** | nothing visible - 1 LSB only |
  | 120 | 262 | 188 | 54 px of one fx dust dot, rest 1 LSB |
  | 300 | 241 | **1** | nothing visible - 1 LSB only |
  | 599 | 96 | 112 | one fx dust dot, rest 1 LSB |
  | KO frame | 108 | **1** | nothing visible - 1 LSB only |

  The 1-LSB pixels are always the same two things: the hp bars' ten tick marks (ink at alpha 0.25 over the bar fill) and the fighters' shadow rows (alpha 0.28 over the floor) - `198,62,117` vs `198,62,118`, `110,65,31` vs `111,65,32`. That is GPU premultiplied-alpha blending at mediump against canvas2d's compositor, not a draw-plan difference. Everything else - arena, sprites (both facings), boxes, hp bar panels and fills, every glyph, and the whole KO panel - is byte-identical to the bar.

  The only visible difference at any tick is a dust particle: canvas2d `arc()+fill` is antialiased and excalibur's circle renderer under `antialiasing: false` is not, so a puff's edge is a hard pixel here and a blended one there. Left as is for the reason the pixi lane gives: forcing it either way means either turning antialias on (which changes what the whole arm is measured at) or reimplementing the bar's circle rasteriser.
