# melonjs cell - defects log

One line per defect hit while building the melonJS 20.4.0 arm: what it was, and
the class it belongs to. Honest and specific on purpose - this log is a ranking
input, so a defect that cost an hour is worth more here than a tidy summary.
This engine had never run on this machine before today, and it is the last of
the seven arms, so several traps below were already paid for by a sibling lane
and are marked as such.

## Defects

- 2026-09-12 **`me.video.init()` DOES NOT EXIST in melonJS 20.** The `video` namespace this version exports is four renderer CONSTANTS (`AUTO`/`CANVAS`/`WEBGL`/`WEBGPU`) and nothing else; an application is `new Application(w, h, settings)` followed by an awaited `app.init()`, and an Application whose `init()` has not resolved has no renderer at all. The engine notes for this lane carried the old call, so the design this lane was handed described an API that was removed. Class: a signature recalled rather than read - the same class as the littlejs lane's `TileInfo` third parameter. Cost nothing because `node_modules/melonjs/build/index.d.ts` was read before the first line was written; it would have cost the whole lane if it had not been.
- 2026-09-12 `preferWebGL1` is not an option in v20 either - `ApplicationSettings` has no such key, so `Partial<ApplicationSettings>` rejects it as an excess property at compile time. It is also unnecessary by construction: `renderer: video.WEBGL` means **WebGL 2 or reject** since 20.0. Class: an option that existed in an earlier major and reads as harmless. Caught by reading `application/settings.d.ts`, before the first build.
- 2026-09-12 **`Renderer.setColor()` MULTIPLIES the incoming colour's alpha by the alpha the renderer is already carrying** - `currentColor.alpha` is both the global alpha and the colour's alpha, and the setter is `const a = currentColor.alpha; currentColor.copy(color); currentColor.alpha *= a`. So an alpha set once for the drop shadow STICKS to every later fill. Worse, `drawImage` takes a quad's alpha from `getGlobalAlpha()` (`currentTint.toUint32(this.getGlobalAlpha())`), so the sprite drawn after a 0.28 shadow is 28% opaque. **MEASURED, not asserted**: deleting the one `setGlobalAlpha(1)` before `drawImage`, rebuilding and re-running the tick-matched diff at tick 120 takes it from **415 px to 5,686 px (2.468%)**, with both fighters washed toward the floor colour (`26,18,48 -> 134,86,54` x1196). Class: a setter that compounds the state it is also reading. Fixed with one `ink(renderer, hex, alpha)` helper that every fill goes through and that always states its alpha.
- 2026-09-12 **`Application.draw()` returns without drawing unless `isDirty || isAlwaysDirty`, and nothing raises.** A cell that stops the engine's loop and calls `app.draw()` itself never runs the engine's UPDATE pass, which is what normally sets `isDirty` - so the first frame paints (the stage change calls `repaint()`) and then the picture FREEZES for the rest of the run. **MEASURED**: with `app.isAlwaysDirty = true` removed, the tick-120 diff goes 415 px -> **13,442 px (5.834%)**, the frame stuck on an early tick - **and `run-tape` still printed `melonjs ADMITTED ticks 600 hash dfd5d033 chain 2617d8f2 eventHash 687c23d3`.** Class: a render gate the caller has to opt out of, whose failure the admission gate structurally cannot see (it reads the sim's hashes, which the drawing never touches).
- 2026-09-12 **`Container.draw` skips any child whose `inViewport` is false**, and `inViewport` is set by the engine's update pass - which a cell driving only `draw()` never runs. A plain `Renderable` added to `app.world` therefore paints NOTHING, with no error, no warning and no clue. **MEASURED**: flipping the plan layer's `floating` to false gives a tick-120 diff of **230,400 px of 230,400 (100.000%)**, every pixel `-> 0,0,0`, a completely black canvas - **and `run-tape` printed `ADMITTED` again**. Class: a retained scene graph gating drawing on state only its own update loop maintains. `floating = true` fixes it and is the right answer for a second reason: melonJS draws a floating renderable in SCREEN space (`resetTransform` + the camera's screen projection), which is exactly the contract's view-pixel space, y down, no flip and no fudge.
- 2026-09-12 the engine owns a `requestAnimationFrame` loop the contract has no method for: `state`'s run loop, started by `_switchState` when the default stage comes up at the end of `init()`. Left alone it renders at its own rate and the sweep would compare a different number of drawn frames per arm. Class: an engine that owns a loop the contract has no method for - the same one pixi's ticker, phaser's display list and littlejs's `engineStep` posed. Fixed with `state.stop()` after init and one `app.draw()` in `endFrame`. **MEASURED on the right axis**: with `state.stop()` removed the page holds **2** queued rAF callbacks after a frame against the canvas bar's **1** (the harness's frame plus the engine's `_renderFrame`), while the PIXEL diff is unchanged at 415 px - so a pixel diff is the wrong instrument for this decision and would have read "no difference" on an arm drawing twice per harness frame.
- 2026-09-12 **melonJS's GL `strokeRect` loses one CORNER pixel per box.** It emits the rect as four `gl.LINES` segments and OpenGL's diamond-exit rule drops each segment's final pixel, so the bar's `?boxes=1` overlay and this arm's disagreed on exactly 4 pixels at tick 120 - each one a solid box colour on the bar (`46,192,138` bdy green, `74,140,255` push blue) and bare floor here. Measured **419 px -> 415 px, maxDelta 199 -> 118** once the outline is built from four `fillRect`s on the integer grid instead. Class: a rasterisation rule that only shows up at the ends of a primitive, and only against a reference. The tell was that every one of the four was an isolated pixel at a box corner.
- 2026-09-12 `failIfMajorPerformanceCaveat` defaults **true** in melonJS, and `renderer: video.WEBGL` REJECTS rather than falling back - so on a machine whose driver chromium flags, the default turns a working arm into a failed `init()`. It is set false here. **NOT a defect that fired**: flipping it back to true, rebuilding and re-running reads **identically** (415 px, WebGL2, samples 0), so headless chromium's SwiftShader context is not flagged on this box. Recorded as a decision with its measurement rather than as a saved catastrophe, because a cost claim with no control is a hypothesis.
- 2026-09-12 my KO probe's first version kept only the LAST frame of the run. `rematchAfterTicks` is 90, so a 6 hp teddy dies, the KO panel shows for `koFadeTicks` 60, and then **the match RESTARTS with full hp** long before the tape's 600 ticks - the final frame is a fresh fight, and both arms read "no KO panel". Two arms agreeing on a wrong answer reads as a fact about the fight, not about the probe; it is the exact shape the phaser4 lane logged for its own KO probe one row further down. Class: `a-diagnostic-that-truncates-what-it-compares` - an instrument sampling at a moment the thing it looks for cannot be at. Fixed by keeping every frame and scanning them all; the unpatched run is the negative control and reads 0.
- 2026-09-12 my first tick-sweep wrapper passed `""` as the dist argument, and the script's `process.argv[2] ?? default` only catches `undefined` - so `resolve("")` became the cwd, every asset 404'd and five ticks in a row failed. Class: a falsy-but-defined argument slipping through a nullish default. `||`, not `??`, for a string that can be empty.
- 2026-09-12 NOT re-paid, because three prior lanes wrote it down: `--outDir` resolves against the config's **root** (`games/fight`), not the cwd, so the flag from `cells/` is `../../dist-fight-melonjs`. Read from `phaser4.md`/`pixi8.md`/`littlejs.md` before the first build and the tree landed in `studio/` first try.
- 2026-09-12 NOT re-paid: the pixel diff is taken from compositor screenshots, never by reading the canvas back inside the page - a GL canvas without `preserveDrawingBuffer` reads cleared after compositing and the diff would have reported 100% (phaser4.md). This arm confirms `preserveDrawingBuffer: false` on its context, so it would have met it.
- 2026-09-12 NOT re-paid: the instrument lives in a lane-private subdirectory of the shared scratchpad, because a peer's `pixel-compare.mjs` overwrote a sibling's there once already (littlejs.md).

## Notes a judge should see (decisions, not defects)

- **GL is ON, WebGL 2, one canvas.** `renderer: video.WEBGL` is WebGL-2-or-reject in v20, so there is no silent 2D fallback to worry about and none was needed: the context came up first try headless with `antialias false`, `alpha false`, `SAMPLES 0`, `drawingBuffer 640x360`, CSS 640x360, `image-rendering: pixelated`. Unlike littlejs this arm has exactly ONE canvas, so `document.querySelector("canvas")` and `stats().backbuffer` cannot disagree.
- **The VIEW mapping is the engine's own screen space.** One `Renderable` marked `floating`, which melonJS draws after `resetTransform()` under the camera's screen projection - one world unit per canvas pixel, y DOWN, which is already the contract's space. No y-flip, no camera arithmetic, no fudge. Proved with `?boxes=1`: the green bdy boxes wrap both fighters head to feet, the blue push boxes sit on the bodies at the feet, and the overlay is pixel-identical to the bar's at every tick measured.
- **The screen shake is a `translate` around the world half of the paint, not a camera move.** The HUD must not shake and the boxes must, and the harness draws boxes AFTER the HUD - so arena/shadows/sprites/fx sit inside one `save`/`translate`/`restore`, the HUD is drawn un-offset, and the boxes carry the offset themselves in a second bracket.
- **Flip is a mirror about the PIVOT column**, `translate(op.x, 0)` + `scale(-1, 1)`, the bar's `drawFrame` geometry one for one - not a mirror about the frame centre. Both sheets happen to have `pivot.x` at the frame's middle, so the two are identical TODAY and would part company on the first character whose feet are off-centre.
- **The pivot comes from the MANIFEST, not the atlas frame.** Both carry one and they agree (robot 0.5/0.7576, teddy 0.5/0.7447), which is exactly why a drift would be silent. The bar reads the manifest, so this arm reads the manifest - phaser4's reasoning, adopted by every lane since.
- **The sheets are decoded with `img.decode()`, not `me.loader`.** Two prior lanes logged a loader that RESOLVES on `image.onerror`, turning a 404 sheet into a blank texture and every fighter into a white slab with nothing thrown. `decode()` REJECTS, which is a failure the admission gate can see; `adopt()` additionally checks the png's natural size against the atlas's own `meta.size`.
- **HUD text is the bar's 5x7 bitmap font, painted as one `fillRect` per lit glyph pixel.** The glyph table is DUPLICATED into this cell rather than imported from `canvas/font.ts`, for the reason the pixi lane logged: a shared import puts a shared chunk in both arms' byte report and moves a number the tournament reads. It costs this arm its share of 3,447 gz authored. There is no text cache either - the bar caches rendered strings and blits, this arm repaints ~140 glyph pixels a frame, which is MORE work than the bar does, not less.
- **`physic: "none"`, `gpuTilemap: false`, `consoleHeader: false`, no input binding, no audio.** Every default melonJS boots is work the plain-canvas bar is not doing and the contract asks for none of it. `consoleHeader: false` removes the renderer and physics header lines from `init()` but NOT the `melonJS 2 (v20.4.0) | http://melonjs.org` banner, which `boot()` logs unconditionally at module load and no setting reaches. It is a `console.log`, so the admission gate - which counts `console.error` - is unaffected; the observed console for a whole tape run is that one line plus the GPU-stall warnings below, and nothing else.
- **The integer upscale goes through the engine's OWN scale setting**, not by writing `canvas.style.width` behind its back: melonJS rewrites those two properties on every resize from `settings.scale`, so the setting is the only place a caller can say it once. `k = floor(min(innerW/640, innerH/360))` is the bar's formula; at the harness's 800x600 viewport both arms land at k=1 and CSS 640x360.
- **The draw plan is kept by reference, never copied.** The harness builds fresh arrays every frame, so `beginFrame` drops the old references and the plan layer's `draw` walks the new ones. A copy would be per-frame work no other arm is doing.
- **`GPU stall due to ReadPixels`** appears four times in the console on this arm under headless swiftshader. It is a driver performance WARNING, not an error, and **pixi8 and littlejs print the identical message on the same build** - so it is a property of compositing a WebGL canvas in this environment, not of this arm. Recorded here so nobody later reads it as one.
- **The KO panel (`phase >= 2`) is UNREACHABLE from the golden tape** - `versus-600` ends at `winner: -1` - so it was exercised the way the canvas and phaser4 lanes exercised theirs: a 6 hp teddy served through `page.route`, at REAL time because `?fast=1` steps 60 ticks per drawn frame while `koFadeTicks` is 60. Both arms drew `KO  ROBOT WINS` with an **identical 178 px ink run** on the panel's border row (canvas at tick 160, melonjs at tick 157 - real-time sampling, not a difference in the sim), and the unpatched run reads **0**, so the probe can tell the two apart.
