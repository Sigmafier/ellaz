# A Choice Stored BY VALUE Freezes Every Option It Could Have Pointed At

**Scope**: `holdem/client/src/lab/**` (the sound strips) and any future picker in this repo that persists what was chosen rather than which one was chosen.
**Origin**: 2026-08-15, adding 110 sound options after the operator asked to have their settled picks stay settled.

## Core Rule

**When a picker stores the CHOSEN THING rather than its id, the option list stops
being code and becomes a persistence format. Editing an option is then a silent
data migration: the audio keeps playing what was picked, and the screen quietly
reads back somebody else's name for it. Options become APPEND-ONLY the moment one
ships - add as many as you like, never edit one - and a checked-in fingerprint
file is what makes that a fact rather than an intention.**

## The shape

Picking a sound in the studio does this:

```ts
setOverride(sfx, arm.spec);   // the whole VoiceSpec, not arm.id
```

which is the right call for the AUDIO. The pick keeps playing exactly what was
auditioned even if `candidates.ts` is rewritten under it, and the override gate
re-validates it on the way back in. It is also the right call for a lab whose
arms are generated by helpers: an id would have to resolve through code that has
moved.

What it leaves behind is the LABEL. Nothing on disk says *which arm* this was, so
`pickedSounds()` recovers it by comparing:

```ts
const hit = strip.arms.find((a) => JSON.stringify(a.spec) === JSON.stringify(spec));
```

Change one digit of a shipped arm and that comparison finds nothing. The strip
shows no selection, the settled row falls back to the default's name, and the
speakers go on playing the pick. **The one screen whose entire job is to tell
somebody what they chose now disagrees with what they hear**, with no error
anywhere and nothing in the diff that looks like it touched a saved value.

## Why it is worse than a renamed id

A renamed id is the familiar version of this - the shop items and the name-pool
words in the main app both carry "never rename, never reuse" for it. That failure
at least has a name and a natural place to look.

This one has neither. The id is untouched and correct; the arm is present; the
strip renders; every test passes. The only observable is a highlight that is not
where somebody left it, days later, on their own device - which reads as "the app
forgot my settings" rather than as a code change, and is the precise complaint the
lock was added to prevent.

## The mechanism

`client/src/lab/arms.lock.json` holds `strip/id -> length-hash` for every arm, and
`armLock.test.ts` compares. Three outcomes, deliberately different:

| | |
|---|---|
| an arm ADDED | fine, and the point - record it with `UPDATE_ARM_LOCK=1` |
| an arm EDITED | red, naming it, saying whose pick it unlabels |
| an arm REMOVED | red, naming it |

Two positive controls sit beside it, because every assertion above passes
vacuously over an empty lock and an empty lock is what a broken reader produces:
the file must hold more than 150 arms, and the fingerprint must give two different
specs two different answers. Mutation-proven both ways on 2026-08-15 - a single
digit changed in `chip-drop` went red naming `chipClack/chip-drop`, and a planted
lock entry went red naming it as GONE.

**The `current` arm of each strip is deliberately NOT locked.** Picking it stores
nothing at all (`setOverride(name, null)`), so no pick can be orphaned by it, and
`candidates.test.ts` pins it to the shipped voice instead. Moving a shipped voice
has to move its control with it; the two tests together say exactly that.

## When to Apply

- Any picker that persists a chosen object, blob, or config rather than a key
- Adding options to one - append, never edit, and never re-sort (the operator
  navigates by where a button was)
- Reviewing a diff that changes an existing option's value: ask what it does to
  somebody who already chose it
- Deciding between storing an id and storing a value: storing a value buys
  stability of behaviour and costs you the freedom to edit the list
